# Record — 2026-09-29: the validity check and the reviewer

What was added to this skill and to `examples/synthetic_search`, what changed
between the plan and the code, and what was left undone. The full specification
lives in the repository this skill was developed in and is not published with
it; this is the short version that travels with the skill.

## What was built

Two rails, aimed at one problem: a cheap model handed a fixed split and a scalar
will eventually solve the measurement instead of the task, and the reward alone
cannot tell the two apart.

- **A validity check**, per candidate, before scoring.
  `substrate/validity.py` holds four behavioural invariants
  (`labels_in_vocabulary`, `deterministic`, `robust_to_perturbation`,
  `bounded_time`). Label-preserving perturbations come from the corpus grammar
  (`corpus.perturbations`). `measure.measure_source` enforces the check on the
  train split before scoring; a failure leaves `reward` as `None` and sets the
  `validity_failed` zero reason, with the violations in the report.
  `validity.py` is part of the instrument pin. `rt check` runs the guard and the
  check inside the box without scoring.
- **A veto-only reviewer stage** between gate and adopt. `substrate/review.py`,
  `cli review`, `review.toml` (ships disabled), `review.md` (the rubric), and a
  stage in `supervisor.sh`. It can refuse an adoption and never causes one.
- **The same in the skill**: the `experiment-scaffold` contracts and templates
  carry both rails, and `viewer-scaffold` gained an optional reviews section.
  The example's viewer was regenerated by running the skill.

Measured at planning time on 300 rows from `corpus.generate(seed=7, n=300)`,
not on the staged corpus: the shipped artifact passes all four invariants; a
hand-written insertion perturbation failed it on 111 of 176 correct rows; a
deliberately memorising table of 40 rules, each memorising one training row
exactly, had 36 of those 40 rules broken by the perturbation, and one violation
is enough to refuse the table as a whole. Separately, the check costs about
0.013 s on the 1,225 train rows of a default staging (my own single run while
writing the docs).

## What changed between the plan and the code

1. **Perturbations are derived from the grammar.** The first version inserted a
   neutral token after the first word, in `validity.py`. It failed the shipped
   artifact, because `good morning ...` became `good really morning ...`, which
   does not mean what it did. Only the module that owns the grammar can make a
   rewrite label-preserving by construction, so `perturbations` moved into
   `corpus.py`.
2. **`review.toml` is its own file.** The eval framework parses `config.*.toml`
   and both must stay identical apart from three fields; the reviewer's provider
   is independent of the rollouts', so a block there would have been wrong twice.
3. **Reviews ride on `/api/state`, not a new route.** It is already the
   page's one state call; a separate route would add a golden entry and a
   normalisation case for nothing the page needs.
4. **The time budget is not tunable from the environment.** It is frozen
   instrument: an environment override would change verdicts while the
   instrument pin stood still. Tuning it is a code edit to a pinned file.

## What execution changed

1. **An unreadable envelope is absence, not a pass.** The plan treated any
   unparseable response as a pass. That is right for a completion whose text
   holds no verdict, and wrong for a body that is not JSON, holds no completion
   or is an error page: that is no reviewer at all. It is now retried, then stops
   the run.
2. **Citations are restricted to changed lines.** A quote must be at least 8
   non-space characters and must appear in the diff's added or removed lines.
   Context lines and file headers no longer ground a refusal; a removed line does,
   because deleting a guard can be the cheat.
3. **The reference run accumulates rules.** Its scripted agent now adds rules
   generation over generation, so it shows three adoptions and a refused fourth
   generation. It previously showed one adoption.
4. **The viewer skill gained a Regenerate procedure**, which is how the
   example's viewer was brought up to date.

Also settled while executing: `bounded_time` times the whole check, and a
non-string label is a `labels_in_vocabulary` violation.

Fixed at the final review, each with a test that failed first:

- **The template `cli.py` gained the example's catch-all**, so an unforeseen
  exception is exit 2, not a refusal the supervisor would silently absorb.
- **Any review outcome other than a pass discards the candidate**, an absent
  reviewer, an unset key and a missing rubric included; before, `adopt` could
  adopt what no reviewer had approved.
- **A cited refusal anywhere in the reply is the verdict**, so an echoed
  `{"decision": "pass"}` planted in the diff cannot override it. `content: null`
  is absence, content in parts is joined and read, and every `[review]` value
  is type-checked.
- **Every validity pass and the scoring load a fresh table.** One shared
  instance let a table count its calls and cheat only once scoring began.
- **`cli review --check`**, run by the preflight, finds a misconfigured
  reviewer before generation 0.

## Deferred

- **Validity violations are not persisted to any file.** They surface in three
  places today: the `violations` field of `promote.rank`'s entry (the
  `validity_failed` branch in `promote.py`; `promote` itself prints only the
  verdict, so this entry is transient), the output of `rt check` inside the box,
  and the JSON printed by `cli score --source`. Re-running the last is the only
  way to see them after the fact.
- **`gate_report.json` carries no generation**, so a report cannot be tied to
  the generation it judged without the surrounding log.
- **`taskset._score_on_host` does not catch `subprocess.TimeoutExpired`.** A
  table that never finishes is bounded by `SCORE_TIMEOUT` during rollout
  scoring, but the expiry is not translated into a named outcome. `promote`,
  `gate`, `adopt`, `review` and `rt` measure in-process with no timeout at all,
  so such a table hangs them.
